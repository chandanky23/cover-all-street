# Duppy Map — Architecture Decisions

Append-only log of decisions and rationale. See `plan.md` for the full spec
these decisions implement.

## 2026-11-06 — Project scaffold and core native stack

- **Framework:** Expo SDK **58** (`expo@58.0.23`), React Native **0.88.1**,
  React **19.3.0**, Expo Router (typed routes), TypeScript `~6.0.3`.
  Chosen because it's the current Expo SDK available on npm at project start
  and satisfies MapLibre's peer requirements below.
- **Map renderer:** `@maplibre/maplibre-react-native@^11.5.1`. Its published
  peer deps require `expo >=54.0.0`, `react-native >=0.80.0`,
  `react >=19.1.0` — satisfied by the chosen Expo SDK. It cannot run inside
  Expo Go; the project uses a custom dev client (`expo-dev-client`) and
  native prebuild (`android/` is a generated, git-ignorable-by-default but
  currently committed-as-generated directory — see note below).
- **Location/background work:** `expo-location` (foreground + background
  permission flow, Android foreground-service flag enabled via plugin
  config) and `expo-task-manager` (background task registration) per
  `plan.md`'s architecture diagram. Not yet exercised on a device — see
  `docs/QA.md`.
- **Local storage:** `expo-sqlite` for all on-device tables (settings,
  geo dataset, areas, street segments, observations, segment_visits,
  area_visits, segment_traversals). No remote database.
- **Package identifiers:** `com.duppymap.app` (Android package / iOS bundle
  id), app name "Duppy Map", scheme `duppymap`. Matches plan.md Phase 6
  guidance.
- **Android SDK/toolchain found on this machine:** Android Studio + SDK at
  `~/Library/Android/sdk` (build-tools, platform-tools, emulator images,
  SDK licenses already accepted). Java 17 (Temurin) at
  `/usr/libexec/java_home -v 17`. `ANDROID_HOME` was **not** exported in the
  default shell profile — each build command exports it explicitly, or
  `android/local.properties` pins `sdk.dir`. No physical Android device or
  running emulator was connected at scaffold time.
- **`expo-doctor`:** 20/20 checks passed after installing the above
  dependencies and configuring `app.json` plugins.

## Open items / not yet decided

- Whether `android/` (native project generated by `expo prebuild`) is

- Release signing key generation/storage strategy — deferred to Phase 6

## 2026-11-07 — Geo dataset pipeline (Phase 2) and tile/basemap source

- **Tile/basemap source, resolved:** bundle a static, versioned dataset
  (administrative boundaries + eligible street segments as GeoJSON,
  processed once at build time) inside the app, rendered via MapLibre
  `GeoJSONSource` + styled fill/line layers — **not** a hosted/online tile
  provider and **not** repeated live queries against any public OSM
  service. This is the only option that is genuinely free indefinitely
  (no account, no usage limits, no dependency on a third party staying
  up), works fully offline (fits the privacy-first/local-only goal), and
  matches plan.md's explicit preference ("prefer a light offline-first
  Berlin vector dataset if feasible") and its ban on bulk-downloading from
  public OSM *tile* servers (we're processing a regional *data* extract
  once, not scraping rendered tiles).
- **Source data:** Berlin OSM extract from Geofabrik
  (`download.geofabrik.de/europe/germany/berlin-latest.osm.pbf`) — the
  standard, OSM-community-endorsed way to get a regional extract for
  offline processing, distinct from hitting a live tile/Overpass server
  repeatedly. Downloaded once into `geo-pipeline/data/` (gitignored —
  regenerated by the pipeline script, not committed).
- **Processing tool:** `osmium-tool` (installed via Homebrew, precompiled
  bottle — no from-source build) to extract administrative boundary
  relations (Bezirke = `admin_level=9`, Ortsteile = `admin_level=10`) and
  the eligible street network (tagged `highway=*`, excluding
  motorway-only/private/inaccessible per plan.md's eligibility rules) and
  convert to GeoJSON.
- **Why not live Overpass API queries:** tried first; the public
  `overpass-api.de` instance was at capacity (502) and a mirror
  (`overpass.kumi.systems`) timed out outright. Public Overpass instances
  are explicitly meant for human/browser use, not automated pipelines —
  using a downloaded extract processed locally is both more reliable and
  the more respectful/correct approach for a reproducible build script.
- **Why not Berlin's official open-data portal:** `daten.berlin.de`
  returned 403 to an automated request at check time; OSM admin
  boundaries (tagged by the same community conventions plan.md references
  for Bezirke/Ortsteile) are the practical fallback and are explicitly
  sanctioned by the plan ("use official Bezirke and Ortsteile rather than
  inventing a universal neighbourhood taxonomy" — OSM's `admin_level`
  tagging for Berlin follows the real official boundaries).
- **Street network v1 scope (2026-11-07):** eligible streets are OSM ways
  tagged `highway` in `{residential, tertiary, secondary, primary,
  unclassified, living_street, pedestrian}`. Explicitly **excludes**
  `footway`/`cycleway`/`path` — tested on Friedrichshain-Kreuzberg and
  found these outnumber named streets ~3:1 (11,205 footways vs. 4,466
  named-street ways in that one district alone), which would roughly
  triple the bundled dataset size for segments that are sidewalks/park
  paths rather than the named streets the app's "streets you've walked"
  concept is actually about. Can be revisited later if walked-path
  coverage turns out to matter for the gift, but starting narrower is the
  reversible choice (easy to add tags back; hard to trim a shipped
  dataset users already have cached expectations around).
- **Fetch strategy:** one Overpass query per Bezirk (not all of Berlin in
  one request) — keeps each query comfortably under Overpass's practical
  size/timeout limits and is a bounded, one-off, politely-paced (3s
  between requests) use of the shared public server, not a production
  dependency. Results are deduplicated by OSM way id when merged (a way
  exactly on a district boundary can be returned by both neighboring
  queries). Coordinates rounded to 5 decimal places (~1.1m precision —
  comfortably finer than consumer GPS accuracy) and only the fields the
  app needs (`id`, `name`, `highway`) are kept, both purely to control
  bundle size with no loss of anything the app uses.
- **Large-asset loading architecture (2026-11-07):** the 26MB
  `berlin-streets.geojson` is registered as a Metro **asset** extension
  (`metro.config.js`) and resolved at runtime to a `file://` URI via
  `expo-asset`, then passed as a *string* to `GeoJSONSource`'s `data`
  prop — never imported/required as a parsed JS module like the much
  smaller Bezirke/Ortsteile files. Confirmed on-device that importing it
  as a normal JSON module gets the app OOM-killed (Hermes allocating 99k+
  parsed Feature objects blows past ~1GB resident). Additionally, the
  `GeoJSONSource` itself is only *mounted* (not just zoom-filtered via the
  `Layer`'s `minzoom`) once the camera's `onRegionDidChange` zoom crosses
  the street-detail threshold — MapLibre parses an entire mounted source
  into native heap regardless of whether any layer using it is currently
  visible, confirmed via `dumpsys meminfo` (~650–740MB mounted vs. ~275MB
  unmounted at the same camera position). See `docs/STATUS.md`'s Phase 2
  entry for full detail and the deferred vector-tile follow-up.
- **Typography (2026-11-07):** Quicksand (OFL, Google Fonts) is the
  app's "friendly rounded sans for interface" (plan.md). Bundled as three
  static instances (Regular/SemiBold/Bold) in `assets/fonts/`, loaded via
  `expo-font`. Each `src/constants/duppyTheme.ts` `type` level sets its
  own `fontFamily` for the matching weight rather than `fontFamily` +
  `fontWeight` — Android does not reliably synthesize bold/semibold for a
  custom typeface the way it does for system fonts, so components must
  pick the named weight file directly or risk a double-bolded render or a
  silent fallback to the system font.
- **Coverage-fill expressions must never be an empty `match` (2026-11-07):**
  `['match', ['get','name'], fallback]` with zero label/output pairs is
  invalid MapLibre style syntax and crashes the layer to solid black with
  a native error toast — found while deliberately testing the "zero
  observations" empty state plan.md requires the map to stay functional
  through. `src/app/index.tsx`'s `coverageFillExpression()` helper now
  returns a flat color instead of building a `match` expression when
  there are no entries. This is a real edge case, not just a test
  artifact: any district/Ortsteil set with no coverage data (a genuinely
  new user, before Phase 4's real data exists) hits it.
- **Onboarding gate must not route to a non-tab screen (2026-11-07):**
  `welcome.tsx` is not one of `AppTabs`' `NativeTabs.Trigger` screens.
  Using `expo-router`'s `Redirect`/`usePathname()` to send a first-time
  user to `/welcome` from the root `_layout.tsx` (which always renders
  `<AppTabs/>`) caused a redirect loop — `AppTabs` doesn't recognize
  `/welcome` as one of its own routes and falls back to its default tab,
  flipping pathname back, triggering the redirect again, visible
  on-device as the whole app flashing continuously. Fixed by rendering
  `WelcomeScreen` directly as a component from `_layout.tsx` (passing an
  `onDone` callback) instead of navigating to its route at all, bypassing
  the tab navigator entirely while onboarding isn't complete.
- **Adaptive location sampling = `distanceInterval`, not a custom
  scheduler (2026-11-07):** plan.md asks for "adaptive location
  accuracy/intervals and battery-aware batching." Implemented as
  `distanceInterval: 15` on `startLocationUpdatesAsync` rather than
  building logic to detect stillness and stop/restart the subscription
  with different settings — the native FusedLocationProvider
  (expo-location's underlying mechanism) already withholds callbacks
  entirely when the device hasn't moved that far, so battery cost scales
  down automatically without this app risking missed updates from
  cycling its own subscription. This is the standard way this is done,
  not a shortcut.
- **Matching runs against per-district files, not the city-wide
  dataset (2026-11-07):** `src/lib/streetGraph.ts` loads one Bezirk's
  streets at a time from the same per-district files the fetch pipeline
  produced before merging them for map rendering, rather than the full
  99k-feature `berlin-streets.geojson`. Reuses `findDistrictForPoint`
  (point-in-polygon against the Bezirke boundaries) to pick which file.
  Keeps matching's memory cost bounded to a few thousand ways regardless
  of city size, consistent with the Phase 2 lesson about not parsing the
  full dataset into JS.
- **Don't wrap idempotent schema DDL in an explicit transaction
  (2026-11-07):** found a real bug where `BEGIN`/`COMMIT` around a
  migration step's `CREATE TABLE IF NOT EXISTS` statements, combined
  with a `PRAGMA user_version` write in the same step, left
  `user_version` bumped on-device while the tables never actually
  persisted (confirmed by pulling and inspecting the db file directly).
  Since every DDL statement here is already safe to re-run, `src/lib/
  db.ts`'s `migrate()` no longer wraps these steps in transactions at
  all — removes the bug without needing to fully root-cause the exact
  SQLite/driver interaction that caused it. Transactions are still used
  for actual data writes (`upsertSegmentVisit`, `seedAreasIfNeeded`,
  etc.) where atomicity genuinely matters.
- **Attribution requirement (not optional):** every screen showing this
  data must credit "© OpenStreetMap contributors" per ODbL — already
  planned for the Settings screen (see Phase 1 mock) and must also appear
  near/on the map itself before Phase 6 sign-off.


## 2026-11-07 — Pre-release hardening: decisions made and why

Each of these was a judgment call, listed so none is silent.

- **Offline map, no INTERNET permission.** The base style is an inline
  background; all drawing is bundled GeoJSON. Chosen so the "nothing leaves
  the phone" claim is provable at the OS permission level.
- **Android cloud backup disabled (`allowBackup=false`).** Auto Backup would
  copy the app database to the user's Google account, contradicting "no cloud
  storage of location data". Replaced by an explicit, user-controlled backup
  file (Settings > Back up / Restore).
- **Light theme only.** The design is the cream/sage/lavender palette;
  following system dark mode produced a half-dark app. Locked to light.
- **Tracking starts automatically after onboarding** once location permission
  is granted, and resumes on app open if the user had it on. Previously the
  user had to find a Settings switch, so a gift recipient could record nothing.
  After a phone restart Android cannot start it without the app being opened.
- **GPS fix filtering** (`fixFilter.ts`): reject accuracy > 35 m, jumps > 50
  m/s, and stationary jitter (device speed < 0.5 m/s, or < 12 m from the last
  stored point at < 0.8 m/s). Enforces plan.md "never count stationary jitter".
- **Matching**: accept a street within 25 m. A competing street only makes a
  match "ambiguous" if it has a *different name* and is within 8 m; other
  pieces of the same street (OSM splits, dual carriageways) are not competitors.
  Measured on simulated walks along real Berlin streets (6-10 m noise): 72-89 %
  of fixes on the right street, 0-1 % on a wrong one, the rest rejected.
- **A "pass"** is a visit separated from the last by >= 10 minutes. Passes are
  stored per street per Berlin day; top streets are ranked by street name.
- **Hourly chart** counts matched GPS points per Berlin hour: relative
  activity, not exact minutes.
- **Neighbourhood (Ortsteil) coverage** is visited / not visited; only the 12
  districts have a real percentage (no per-Ortsteil street length exists).
- **No travel-mode detection.** Cycling or transit along streets is counted
  as "streets travelled" (plan.md: label the metric accordingly).
- **Berlin only.** Points outside the 12 districts are ignored.
- **Percentages** below 1 % show decimals so first walks are visible.

## 2026-11-07 — Journey tagging (v1: whole journey)

- A **journey** is a run of recorded fixes with no 10-minute pause; stationary
  fixes are never stored, so a long stop ends a journey. Journeys under 300 m
  or 3 minutes are not shown.
- The person tags a whole journey as Walking, Cycling, Bus, Tram, U-Bahn /
  S-Bahn, Train, Car / taxi or Other. The app only *suggests* walking, cycling
  or "a vehicle" from speed; it cannot tell bus from train from car.
- Journeys are stored (thinned route preview, distance, speed buckets, tag) in
  a `journeys` table because raw points are purged after 7 days. Included in
  backup/restore and cleared by Delete all data.
- "How you travelled" in Insights sums journey distance per mode within the
  active time filter; untagged journeys are shown as "Not tagged", never guessed.
- **Not in v1 (planned v2):** splitting one journey into fragments with
  different modes. Tagging does **not** change street colouring or the
  walking-pass counts: those still mean "streets travelled" in any mode.
